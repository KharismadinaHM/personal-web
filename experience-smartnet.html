1. Ringkasan & Ruang Lingkup Proyek

Arsitektur data streaming berskala besar end-to-end yang menyerap data transaksi kasir toko dan master data cabang ke dalam BigQuery Medallion Data Warehouse, dilengkapi sistem observabilitas proaktif dan penyajian BI real-time.

  • Komponen yang saya bangun:
    • Streaming Dataflow Ingestion Layer: Raw ingestion dari 20 stream Pub/Sub, pembersihan data (in-flight cleansing), deduplikasi stateful, dan pemuatan ke layer bronze (staging) BigQuery via Storage Write API.
    • Transformasi Bronze ke Silver: Pipeline Dataflow otomatis untuk standardisasi dan pembersihan data lebih lanjut.
    • CDC Master Data Cabang: Alur Google Cloud Datastream untuk menangkap perubahan data master dari basis data cabang ke BigQuery.
    • Observabilitas Grafana 1.200 Toko: Monitoring live transfer data, keterlambatan (late data), dan pencegahan data loss pada seluruh 1.200 gerai toko.

3. Detail Implementasi: Pipeline Streaming Dataflow

Satu streaming Dataflow job terpadu menangani 10 tabel sumber dari 2 tipe toko (total 20 subscription Pub/Sub dan 20 tabel BigQuery bronze). Pipeline dibangun secara dinamis berbasis loop konfigurasi tanpa perlu deploy job terpisah per tabel.

Tahap Komponen Fungsi & Logika Pemrosesan
1. Read Pub/Sub I/O Membaca streaming messages dari 20 subscription Pub/Sub secara paralel.
2. CDC Prepare JSON Parser & Formatter Parsing payload JSON, klasifikasi record UPSERT atau DELETE, pembuatan sequence number dari waktu operasi (fallback waktu server jika kosong), normalisasi kode toko, tagging tipe toko, dan penambahan ingestion timestamp.
3. Make Dedup Key Key Extractor Membentuk composite key dari nama tabel + primary key (selalu menyertakan kode toko unik).
4. Stateful Dedup Stateful Processing (Beam State API) Menyimpan sequence number tertinggi per key dan mendrop record lama atau duplikat. State otomatis kedaluwarsa setelah 7 hari inaktivitas.
5. Fix Types Defensive Schema Mapper Type casting ketat ke skema BigQuery tujuan, validasi nilai numerik (mencegah error seperti "N/A"), penghapusan kolom operasional redundan, failed cast diubah menjadi NULL dengan peringatan log.
6. Write Storage Write API Penulisan streaming berkecepatan tinggi ke tabel BigQuery bronze.
Side Output Dead-Letter Queue Record yang gagal diparsing ditulis ke tabel error_logs bersama payload asli dan pesan error tanpa memutus pipeline.
  • Keputusan Desain Kunci:
    • 1 Job Terpadu: Shared workers (n2-standard-4, autoscaling 1–4, Streaming Engine) membuat biaya fixed per-job hanya dibayar 1 kali dibanding 20 job terpisah.
    • At-least-once Delivery by Design: Menjamin zero data loss saat jaringan toko tidak stabil; potensi duplikasi diselesaikan oleh stateful dedup berbasis sequence number.
    • Stateful Deduplication: Menjamin urutan data; record out-of-order atau late data tidak akan menimpa data yang lebih mutakhir.
    • Retry Under Load: Pipeline melakukan retry otomatis saat worker mencapai beban maksimal, mencegah data terbuang pada jam sibuk.
    • Preservasi Riwayat Delete: Operasi delete ditandai (cdc_change_type = DELETE), mempertahankan riwayat audit untuk keputusan di silver layer.
    • Defensive Type Handling: Validasi ketat mencegah nilai abnormal merusak Storage Write API; anomali dicatat sebagai NULL dengan log warning.
  • Runtime & Libraries: Apache Beam Python SDK (apache_beam), Storage Write API, Streaming Engine Runner v2, stateful timer 7 hari, counters Beam metrics, dan structured JSON logging.

5. Masalah yang Diselesaikan & Dampak Bisnis

  • Streaming Near Real-Time Hemat Biaya: Mengonsolidasi 20 pipeline terpisah menjadi 1 streaming job multi-stream, melayani 1.200 toko (~100 GB/bulan) hanya dengan biaya operasional sekitar $300 per bulan.
  • Mengatasi Ketidakcocokan Data Master: Menemukan akar masalah selisih data akibat gangguan konektivitas toko, diatasi dengan at-least-once delivery + stateful dedup + monitoring proaktif.
  • Deteksi Toko Offline dalam 10 Menit: Toko yang tidak mengirim data langsung terdeteksi dalam waktu 10 menit melalui alert WhatsApp/Email (sebelumnya baru disadari berhari-hari setelah terjadi selisih rekonsiliasi manual).
  • Zero Silent Data Loss: Kombinasi dead-letter error logs dan metrik internal pipeline menjamin tidak ada data transaksi kasir yang hilang secara diam-diam.

5. Masalah yang Diselesaikan & Dampak Bisnis

  • Kasus 1 — Permintaan Funnel Perjalanan Pengguna yang Belum Didukung Data:
    • Permintaan: Stakeholder bisnis meminta analisis funnel perjalanan pengguna (user journey funnel) untuk seluruh alur pemesanan tiket: pembelian tiket, pengembalian dana (refund), dan ubah jadwal (reschedule).
    • Permasalahan: Audit data menemukan bahwa sejumlah layar penting aplikasi belum memiliki tagging event sama sekali, dan sebagian record transaksi/promo tidak valid. Funnel yang dipaksakan dari data ini akan menampilkan persentase drop-off yang salah dan dapat memicu salah ambil keputusan bisnis.
    • Investigasi & Keputusan: Kami mengkomparasi seluruh layar alur tiket dengan log event BigQuery untuk memetakan layar yang tidak terlacak. Kami mengomunikasikan temuan ini secara transparan dalam bahasa bisnis dan menyepakati penundaan singkat untuk memperbaiki tagging di aplikasi terlebih dahulu sebelum funnel dibuat.
    • Hasil: Klien terhindar dari keputusan bias dan berhasil memperoleh metrik funnel yang 100% akurat dan dapat diandalkan.
  • Kasus 2 — Menjinakkan 100 GB/Hari Event Mentah Bersarang Menjadi Data Mart Cepat:
    • Tantangan: Event mentah Firebase memiliki format sangat bersarang (nested arrays), rekaman berulang akibat pengiriman ulang jaringan mobile, dan berukuran ~100 GB/hari sehingga sangat berat dan lambat jika di-query langsung oleh tim analitik.
    • Solusi: Medallion warehouse yang melakukan flattening dan deduplikasi otomatis di silver, lalu memodelkannya ke Star Schema di gold.
    • Hasil: Tim bisnis dan BI memperoleh dashboard perjalanan tiket yang responsif, kueri cepat, hemat biaya komputasi BigQuery, dan berbasis tabel data yang konsisten di seluruh departemen.
